# 구현 경험

## 답만 맞아도 오류 분석 전제와 고정 조사가 틀릴 수 있음

- 증상: 5학년 전수 편집 읽기에서 `최대 몇 개을`, `기온 경보 기준가`
  같은 고정 조사 오류가 6개 템플릿에서 재현됐다. 분수 비교 오류 분석
  6개 템플릿은 `분모만 보고 더 작은 가`, `분자만 보고 더 작은 나`라고
  썼지만 실제로도 각각 가와 나가 더 작아서 잘못된 판단을 분석한다는
  전제가 성립하지 않았다. 정답식과 선택지는 맞았기 때문에 기존 답
  검증만으로는 드러나지 않았다.
- 원인: 생성 프로필의 단위·문맥 뒤에 하나의 조사를 일괄 덧붙였고,
  오류 분석 문장은 실제 두 분수의 대소 관계와 반대인 오개념 주장을
  별도 계약으로 검사하지 않았다.
- 실패한 접근: 숫자 뒤 조사 교정기는 `몇 개을`, `기준가`처럼 숫자와
  붙지 않은 고정 문구를 고칠 수 없다. solver·선택지·풀이에 정답이
  들어 있는지만 확인하면 우연히 맞는 잘못된 추론 전제도 통과한다.
- 대응: 올림·버림 생성 설정에 `장을/개를/권을`의 목적격 조사를
  명시하고, 범위 생성 설정에는 `나이가/기준이/권수가/번호가`처럼
  완성된 주어 형태를 명시했다. 분수 비교의 두 오류 분석 문제는
  학생이 실제로 더 작은 수를 더 크다고 고르게 문장을 바로잡았다.
  전수 변형 감사에는 잘못된 고정 조사와 두 오류 분석 문제군의
  필수 오개념 주장을 회귀 조건으로 추가했다.
- 확인: 수정 전 고정 조사 오류 174개 변형과 오류 분석 원문 6개가
  실패하는 것을 확인했다. 수정 뒤 780개 템플릿의 196,167개 허용
  변형에서 문장·답·선택지·힌트·풀이·시각 문자열 결함이 0건이다.
  780개 명시적 편집 결정에는 수정한 12개 원문의 해결된 `wording`
  finding을 남겼다.
- 유지 계약: 정답 일치만으로 오류 분석 문제를 통과시키지 않는다.
  문제군이 잘못된 판단을 전제로 하면 그 판단이 실제 비교 결과와
  반대인지 검사한다. 숫자와 붙지 않은 단위·문맥 조사는 생성 프로필의
  완성 문장으로 검수하며 런타임 숫자 조사 교정기에 의존하지 않는다.

## 숫자 뒤 조사를 템플릿에 고정하면 매개변수 값에 따라 문장이 깨짐

- 증상: 5학년 가능성 풀이에서 `77가 72보다 큽니다`, 분수 풀이에서
  `6/12를 기약분수로 나타냅니다`처럼 숫자·분수의 실제 끝소리와
  조사가 맞지 않았다. 780개 원문의 허용 매개변수 196,167개를 모두
  펼치자 19개 개념, 151개 템플릿에서 30,239개 잘못된 조사 표면이
  재현됐다.
- 원인: `{{expression}}가`, `{{fraction}}를`처럼 조사 하나를 JSON
  템플릿에 고정했고 문제 생성기는 수식 값만 치환했다. 같은
  템플릿이라도 결과의 마지막 숫자나 분수의 분자가 달라지므로 원문
  단계에서 하나의 조사로 맞출 수 없다.
- 실패한 접근: 대표 seed 몇 개만 검사하면 넓은 반올림·올림·버림
  범위에서 드문 끝자리 결함을 놓친다. 분수의 분모 또는 문자열 마지막
  숫자로 조사를 고르면 `5/18가`처럼 실제로 읽는 분자를 반영하지
  못한다. 나눗셈 슬래시까지 분수로 처리하면 `12/5으로 나눕니다` 같은
  정상 나눗셈 문장도 바뀐다.
- 대응: 5학년 문제 생성 직후 문제·선택지·힌트·풀이의 완성된 숫자,
  분수, 단위 표면을 공통 교정기로 처리한다. 분수는 `분모분의 분자`의
  마지막 소리인 분자를 기준으로 하고, `으로/로`는 ㄹ 받침 예외를
  적용하며, 실제 나눗셈 슬래시 표면은 제외한다. 6학년 생성 결과는
  기존 검수 영수증을 임의로 무효화하지 않도록 이 변경에서 건드리지
  않았다. 5학년의 텍스트·시각 검수 버전에는 교정기 버전을 포함해
  콘텐츠 해시가 이전 영수증을 재사용하지 못하게 했다.
- 확인: 독립 조사 표와 대표 숫자·분수·단위·나눗셈 말뭉치 9건을
  통과했다. 780개 템플릿의 196,167개 허용 매개변수 조합에서 문제,
  정답, 선택지, 힌트, 풀이, 그림 문자열을 다시 감사해 잘못된 조사,
  미평가 수식, 중복 선택지, 정답 누락이 모두 0건임을 확인했다.
- 유지 계약: 매개변수 뒤 조사를 대표 숫자 하나로 고정해 검수하지
  않는다. 5학년 텍스트 생성 규칙이 바뀌면 검수 버전을 올리고 모든
  허용 조합을 다시 감사한다. 분수 조사는 분자를 기준으로 하되 실제
  나눗셈 슬래시는 바꾸지 않는다.

## 미션을 다시 열 때 실행 ID를 바꾸지 않으면 정답 시도 영수증이 사라짐

- 증상: 3학년에서 한 문제를 틀린 뒤 다른 미션으로 이동했다가 원래
  미션으로 돌아와 정답을 맞히면 완료·복습·보상은 정상 반영됐지만,
  `mathAssist_attemptReceipts_v1`에는 첫 오답만 남았다. 새 정답 확인이
  같은 `attemptId`로 중복 처리되어 `[false, true]`가 아니라
  `[false]`가 되었다.
- 원인: 미션 이동은 `wrongAttemptCount`를 0으로 초기화하면서
  receipt의 `sessionRunKey`에는 같은 날짜 seed와 재시작 순번을 계속
  사용했다. 따라서 재진입 뒤 `attemptOrdinal: 0`이 첫 진입의
  `attemptOrdinal: 0`과 같은 영수증 ID를 만들었다.
- 실패한 접근: 저장소의 중복 판정을 느슨하게 하거나 같은 ID의 결과를
  덮어쓰면 반복 이벤트의 멱등성과 이미 기록한 오답을 잃는다. 오답
  횟수를 미션 사이에 계속 올리면 화면의 새 실행 의미와 순번이
  어긋난다. 검증 중 1학년 재도전 답과 새 콘텐츠 보상을 날짜와 무관하게
  고정값으로 가정한 E2E도 실제 날짜 seed에서 깨졌으므로, 재시도 횟수를
  늘리지 않고 생성된 현재 미션과 콘텐츠 중복 여부를 기준으로 바꿨다.
- 대응: 1·2·3학년 미션 화면은 최초 진입, 다른 미션 선택, 명시적
  재시작, 전체 초기화마다 고유한 `missionAttemptRunKey`를 만든다. 같은
  화면 안의 오답 재시도는 그 키를 유지해 `attemptOrdinal` 0, 1, …로
  기록하고 반복 전달은 같은 ID로 멱등 처리한다. 기존 학년별
  localStorage 키·진도 schema·완료·복습·보상·풀이장 실행 키는 바꾸지
  않았다.
- 확인: 실패 E2E에서 재진입 전에는 `[false]`만 남는 것을 확인했고,
  수정 뒤 `[false, true]`, 순번 `[0, 0]`, 서로 다른 ID 두 개를
  확인했다. 1·2·3학년 집중 브라우저 검사 4/4, 전체 Vitest 69개 파일
  624/624, lint, TDD guard, 정적 build 113/113, 단일 작업자 전체 E2E
  76/76이 통과했다.
- 유지 계약: 한 미션 진입 안의 반복 이벤트는 같은 실행 키를 쓰고,
  미션을 떠났다가 돌아오거나 재시작한 뒤의 새 확인은 다른 실행 키를
  쓴다. 영수증 충돌을 해결하기 위해 기존 영수증을 덮어쓰거나 학년별
  진도를 바꾸지 않으며, 형식 오류는 계속 영수증과 시도 순번을 만들지
  않는다. 날짜 seed가 다른 콘텐츠를 반드시 만든다고 테스트에서
  가정하지 않는다.

## 곡면 입체를 기호로만 그리면 반복 계수와 전개도 오류가 분리됨

- 증상: 원기둥·원뿔·구를 작은 아이콘 하나로만 보여 주면 여러 개의
  밑면·굽은 면·꼭짓점을 세는 응용과 전개도의 누락·과잉 조각을
  실제 그림에서 검산할 수 없다. 첫 모바일 화면의 단일 입체도형도
  200px 카드 안에서 약 60px로 보여 여백이 지나치게 컸다.
- 원인: 도형 종류, 반복 수, 원기둥 전개도의 실제 원·직사각형 수를
  함께 소비하는 정량 시각 모델과 반복 수에 따른 자동 배치가 없었다.
- 실패한 접근: 모든 문제에 한 개의 대표 그림만 두면 `p`개에 대한
  합산 답과 DOM의 도형 수가 일치하지 않는다. 한 개와 여섯 개에 같은
  고정 크기를 쓰면 한 개는 너무 작고 여러 개는 겹친다.
- 대응: `round-solid`은 원기둥의 두 밑면·굽은 면, 원뿔의 밑면·
  굽은 면·꼭짓점, 구의 굽은 면을 종류와 `copies`에서 파생한다.
  `cylinder-net`은 각 복사본의 실제 `circleCount`와
  `rectangleCount`를 그린다. 1개는 크게, 2~3개는 한 줄, 4~6개는
  격자로 배치하고 개념·문제 화면이 같은 렌더러를 사용한다.
- 확인: 1~6개 모든 배치의 SVG 경계와 구성 요소 수, 원 1·2·3개,
  직사각형 0·1개 전개도를 검사했다. 390×844에서 단일 원기둥·원뿔·
  구와 5개의 누락 전개도를 직접 확인했고 가로 넘침, 답 메타데이터,
  하단 행동과 동반자 겹침, 콘솔 오류가 모두 0이었다. 전체 Vitest
  65개 파일 517/517, lint, TDD guard, validator·audit 오류·경고 0,
  build 93/93, E2E 61/61이 통과했다.
- 유지 계약: 반복 문제의 prompt·solver·풀이·SVG는 같은 `copies`를
  사용한다. 전개도는 실제 조각만 DOM에 만들고 누락·과잉 정답 문구를
  미리 넣지 않는다. 단일·최대 반복 수를 모두 모바일에서 검수한다.

## 다면체의 이름·개수·그림을 따로 만들면 정량 관계가 깨짐

- 증상: 각기둥·각뿔 문제를 이름 맞히기와 공식 암기로만 만들면
  밑면의 변 수에서 면·모서리·꼭짓점을 체계적으로 세는 활동과 전개도
  오류 분석이 분리된다. 첫 실화면에서는 연습 SVG는 보였지만 개념
  페이지의 새 시각 자료 형식을 기존 `VisualAid`가 소비하지 못해
  제목 아래가 비어 있었다.
- 원인: n각형 밑면, 두 밑면의 대응점, 꼭대기점, 전개도의 밑면과
  옆면 조각을 하나의 정량 시각 계약으로 표현하는 형식이 없었고,
  문제용 렌더러와 개념 설명용 렌더러의 소비 경계도 달랐다.
- 실패한 접근: 면·모서리·꼭짓점 공식을 글로만 반복하면 실제 계수,
  역산, 복합 포장, 누락·과잉 전개도 추론을 검증하지 못한다. 새
  시각 형식을 JSON에만 넣으면 타입 검사는 통과해도 화면은 빈
  컨테이너를 만들 수 있다.
- 대응: `poly-solid`는 정 n각형의 꼭짓점에서 두 밑면·옆 모서리 또는
  밑면·꼭대기점을 파생하고, `prism-net`은 밑면 변 수와 실제 옆면·
  밑면 조각 수에서 전개도를 만든다. 두 형식을 문제와 개념 시각 자료가
  같은 렌더러로 소비하게 하고, 개념 자료 렌더링 회귀 테스트를
  추가했다.
- 확인: n=3~8에서 각기둥·각뿔의 밑면·옆 모서리·꼭짓점 위상과 완전·
  누락·과잉 전개도의 조각 수, SVG 경계를 검사했다. 390×844에서
  오각기둥·오각뿔·오각기둥 전개도를 직접 확인했고 가로 넘침, 제출 전
  답 메타데이터, 하단 행동과 동반자 겹침, 콘솔 오류가 모두 0이었다.
  전체 Vitest 65개 파일 507/507, lint, TDD guard, validator·audit
  오류·경고 0, build 90/90, E2E 59/59가 통과했다.
- 유지 계약: 문제·정답·풀이·SVG는 같은 밑면 변 수를 사용한다. 시각
  설정에는 파생된 정답 필드를 넣지 않으며, 새 문제 시각 형식은 문제
  카드뿐 아니라 개념 설명용 소비자에서도 실제 렌더링을 검사한다.

## 삼각형 이름과 그림을 다른 데이터에서 만들면 분류 근거가 깨짐

- 증상: 이등변·정삼각형과 예각·직각·둔각삼각형을 함께 분류하는
  4학년 공개 단원이 없었다. 분류 이름을 미리 정하고 장식용 삼각형을
  그리면 표시된 변과 직각 표식이 정답 근거와 달라질 수 있다.
- 원인: 세 변에서 삼각형 부등식, 꼭짓점 좌표, 변 분류와 각 분류를
  함께 계산하는 정량 모델이 없었다.
- 실패한 접근: 변 기준과 각 기준을 별도 문제로만 나누면
  이등변직각삼각형·이등변둔각삼각형처럼 두 이름이 겹치는 추론이
  빠진다. 첫 실화면에서는 좁은 이등변삼각형의 두 변 라벨과 하단
  안내 문구가 겹쳤다.
- 대응: 세 변으로 꼭짓점 좌표를 계산하고 같은 모델의 제곱 관계로

## 도형 이동은 문제 좌표와 그림을 별도로 계산하면 목표 위치가 어긋남

- 증상: 4학년 공개 범위에는 밀기·뒤집기·돌리기와 점의 좌표 이동을
  함께 연습하는 단원이 없었다. 문제 문장에서 좌표 답을 계산하고 SVG는
  고정된 전후 그림을 쓰면 이동량·기준선·회전 중심이 바뀔 때 그림의
  목표 위치가 정답과 달라질 수 있다.
- 원인: 시작점, 이동량, 뒤집기 기준선, 회전 중심을 하나의 변환
  함수로 소비하는 계약이 없었다. 목표 좌표를 시각 설정에 미리 넣으면
  가리더라도 제출 전 답 전용 데이터가 남는다.
- 실패한 접근: 이동 이름만 맞히는 문제로 채우면 `[4수03-05]`의
  위치·방향 설명과 연속 이동 추론이 빠진다. 시작점과 목표점을 모두
  SVG에 먼저 그리고 CSS로 목표를 숨기는 방식도 DOM 답 선노출을
  막지 못한다.
- 대응: `slide`, `flip-vertical`, `rotate-clockwise`,
  `slide-then-flip`, `double-flip`을 시작 위치와 변환 매개변수에서
  계산하는 공통 모델을 만들었다. K4/A4/R2에는 이동 판정, 성질 비교,

  선에 두 번 뒤집기의 역변환을 넣었다. 목표 도형·좌표는 확인 뒤
  렌더러가 계산한다.
- 확인: 10개 문제군의 1~9 변형에서 밀기 덧셈, 세로선 반사,

- 유지 계약: 문제·정답·풀이·SVG는 같은 변환 함수를 사용한다.

  접근성 이름에 만들지 않는다. 좌표 격자는 모바일에서 실물로

  무한 반복해 실제 클릭 사각형을 계속 바꾸고 있었다.
- 실패한 접근: 실패한 테스트만 재실행하면 통과했지만 다른 진행 버튼
  검사에서 같은 원인이 다시 나타났다. 테스트마다 강제 클릭을 쓰면
  움직이는 터치 대상을 제품에 그대로 남긴다.
- 대응: 맥박 효과를 크기 변화 없는 `box-shadow` 애니메이션으로 바꿔
  현재 위치 강조를 유지하면서 버튼 사각형을 고정했다. 회귀 테스트는
  진행 버튼이 맥박 클래스를 유지하되 keyframes에 `transform`이 다시
  들어오지 않는지 검사한다.
- 확인: 집중 회귀 1/1과 배포 환경과 같은 단일 작업자 전체 E2E
  43/43이 통과했다.
- 유지 계약: 클릭 가능한 진행 버튼의 반복 애니메이션은 위치·너비·
  높이·transform을 바꾸지 않는다.

## 동분모 분수 계산도 입력값과 정량 띠를 하나의 모델로 묶어야 함

- 증상: 기존 4학년 단일 입력은 정수와 소수만 구분해 `1/`, `4/6`,
  `1 2/5`를 형식 오류·동치 값·대분수로 나눌 수 없었다. 피연산자를
  글자로만 보여 주면 분모를 유지하는 까닭과 받아내림의 단위 조각도
  확인하기 어려웠다.
- 원인: Bridge 답 형식에 유리수 비교 계약이 없고, 분모와 분자에서
  등분 수·색칠 칸을 만드는 정량 시각 모델도 없었다.
- 실패한 접근: 문자열 완전 일치만 사용하면 `4/6`과 `2/3`, `7/5`와
  `1 2/5`를 서로 다른 답으로 처리한다. 결과 분자를 시각 설정에 함께
  넣으면 제출 전 DOM이나 접근성 이름으로 답을 만들 위험이 있다.
- 대응: 완전한 분수·대분수만 파싱해 정수 교차곱으로 비교하고 분모
  0과 미완성 형식은 채점 가능한 시도에서 제외했다. 분수 띠는 문제에
  주어진 분모와 두 피연산자만 받아 각 막대의 등분 수와 색칠 칸을
  계산하며, 결과 문자열은 정답 확인 뒤에만 렌더링한다.
- 확인: 가분수·대분수 동치와 형식 오류를 분리하고 10개 문제군의
  1~9 변형에서 덧셈·뺄셈·빠진 항을 독립 계산했다. 390×844에서는
  8등분 띠 두 개의 16개 칸, 내부·페이지 가로 넘침 없음, 제출 전
  `5/8` 결과 부재, 분수 입력 키보드와 콘솔 오류 0을 확인했다. 전체
  Vitest 62개 파일 434/434, lint, TDD guard, Grade 4·curriculum
  validator, mission audit 오류·경고 0, build 75/75, E2E 43/43이
  통과했다.
- 유지 계약: 분수 정답을 문자열 하나로만 비교하지 않는다. 정량 띠는
  피연산자와 같은 모델에서 만들고 합·차·빠진 분자는 확인 전에
  시각 설정이나 DOM에 넣지 않는다.

## 소수 입력과 자리표를 일반 숫자로만 다루면 형식·노출 계약이 흐려짐

- 증상: 기존 4학년 입력은 정수만 허용해 `0.09`를 정상 제출할 수
  없었다. 소수 자리 숫자를 표로 보여 주면서 완성된 `2.609`까지
  미리 한 문자열로 만들면 답 전용 합성값이 제출 전 DOM에 남는다.
  첫 모바일 자리표는 내부 최소 폭 300px 때문에 카드 안에 불필요한
  가로 스크롤바도 만들었다.
- 원인: 정수 정규화와 큰 수 자리표만 있던 초기 Bridge 계약에는
  소수점, 끝의 0 동치, 미완성 소수 형식, 소수 둘째·셋째 자리 표현이
  없었다.
- 실패한 접근: `Number(raw) === Number(answer)`만 사용하면 `0.` 같은
  미완성 입력도 숫자 0으로 받아들일 수 있고, 자릿수 의미와 형식 오류를
  구분하기 어렵다. 표 아래에 완성된 소수를 항상 렌더링하는 방식은
  학습자가 구성해야 할 답을 먼저 노출한다. 자리표에 고정 최소 폭을
  두는 방식은 세 칸에는 여유가 있어도 네 칸과 카드 padding이 합쳐져
  모바일 내부 스크롤을 만든다.
- 대응: 완전한 십진 문자열만 받은 뒤 부호·앞쪽 0·소수 끝 0을 문자열로
  정규화해 정확히 비교한다. 자리표는 일·십분의 일·백분의 일·천분의 일
  칸을 각각 렌더링하고, 합성 소수 문자열은 정답 확인 뒤에만 만든다.
  자리 열은 사용 가능한 카드 폭을 같은 비율로 나누고 고정 최소 폭을
  두지 않는다.
- 확인: `0.70 = 0.7`, 다른 값, `.`, `0.`, `-`를 분리하고 소수 단원
  1~9 전 변형의 자릿값·비교·배치·구간·빈칸 답을 독립 계산한다.
  컴포넌트 쌍 테스트는 합성 답의 제출 전 부재와 제출 후 존재를 확인한다.
  390×844 브라우저는 세·네 열 자리표의 내부 `scrollWidth`가
  `clientWidth`를 넘지 않는지 검사한다. 전체 Vitest 61개 파일
  428/428, lint, TDD guard, Grade 4·curriculum validator,
  mission audit 오류·경고 0, build 75/75, E2E 42/42가 통과했다.
- 유지 계약: 소수 채점에 부동소수점 비교만 사용하지 않는다. 미완성
  소수는 오답·진도·receipt를 만들지 않으며, 자리표의 합성 답은 확인
  전 DOM과 접근성 이름에 존재하지 않아야 한다.

## 모바일 고정 캐릭터가 답 입력칸 가장자리를 가림

- 증상: 390px 폭의 4학년 어림 미션에서 고정 수리 배지의 왼쪽 6px가
  답 입력칸 오른쪽 가장자리 위에 놓였다. `pointer-events-none`이라
  입력을 막지는 않았지만 컨트롤 테두리를 시각적으로 가렸다.
- 원인: 모바일 배지는 36px로 축소됐지만 화면 오른쪽에서 8px 안쪽에
  고정되어, 본문 카드의 오른쪽 여백보다 안으로 들어왔다.
- 실패한 접근: 클릭을 통과시키는 것만으로는 ‘동반자가 답안 컨트롤을
  가리지 않는다’는 시각 계약을 충족하지 않는다.
- 대응: 모바일에서 배지를 화면 오른쪽 0px에 맞추고 중간 화면 이상은
  기존 20px 여백을 유지한다.
- 확인: E2E가 입력칸의 오른쪽 좌표보다 배지의 왼쪽 좌표가 작지 않은지
  검사한다. 375px 실제 렌더에서는 입력칸 오른쪽 337px, 배지 왼쪽
  339px로 2px 간격이며 가로 넘침과 콘솔 오류가 없다.
- 유지 계약: 고정 캐릭터의 클릭 통과 여부뿐 아니라 답 입력·선택
  컨트롤과 실제 사각형이 겹치지 않는지 모바일 브라우저에서 검사한다.

## 어림 문제의 정답과 방법 비교가 표시 수에서 파생되어야 함

- 증상: 어림셈은 정확한 계산보다 답의 범위가 넓어, 문제 문장과 별도로
  고정한 어림값도 겉보기에는 그럴듯할 수 있다. 곱을 십 단위와 백
  단위로 어림하는 비교 문제도 수를 잘못 고르면 두 방법의 결과나
  오차가 같아져 정답이 하나로 결정되지 않는다.
- 원인: 어림 단위, 표시 피연산자, 정답, 비교 오차를 하나의 수학
  모델로 묶지 않으면 숫자 변형 때 계약이 쉽게 갈라진다.
- 실패한 접근: 풀이에만 어림 근거를 적거나 대표 예시 하나를 눈으로
  확인하는 것으로는 1~9 변형의 경계와 동률을 막을 수 없다. 특히
  십 단위와 백 단위 어림값이 같아지는 수를 방법 비교에 쓰면 추론
  문제가 사실상 선택 불가능해진다.
- 대응: 모든 어림 답을 `visualConfig`의 표시 피연산자와 명시한
  십·백·천 단위에서 계산한다. 방법 비교는 정확한 곱과 두 어림값의
  오차를 각각 구하고, 허용 변형 전체에서 십 단위 방법의 오차가
  엄격히 더 작도록 수 범위를 구성한다.
- 확인: 덧셈·뺄셈·곱셈·나눗셈과 생활 적용, 잘못된 합 교정, 방법
  비교의 1~9 변형을 독립 계산과 대조한다. 선택지는 네 개가 모두
  다르고 정답이 정확히 한 번만 들어가는지 함께 검사한다. 전체
  Vitest 423/423, lint, TDD guard, Grade 4·curriculum validator,
  mission audit 오류·경고 0, build 75/75, E2E 41/41이 통과했다.
- 유지 계약: 어림 정답을 표시 수와 별도 상수로 작성하지 않는다.
  비교 문제는 두 결과가 다르다는 것뿐 아니라 실제 값과의 오차가
  동률이 아님을 모든 변형에서 검증한다.

## 4학년 단원 추가가 전역 개수와 선수 기준 문자열 때문에 막힘

- 증상: 4학년 검증기는 단원이 늘어도 전체가 정확히 1단원·10문항이어야
  통과하도록 고정되어 있었다. 새 단원에 선수 기준 `[4수01-06]`을
  적자 curriculum validator는 이 문자열까지 현재 4학년 출시 참조로
  세어, 실제 문제에서 사용하지 않는 기준을 `existing-reference`로
  승격하라고 오류를 냈다. 단원을 바꿔도 이전 단원의 문항 위치가
  그대로 이어지는 문제도 함께 드러났다.
- 원인: 최초 Bridge가 한 단원일 때 전역 합계와 단원별 게이트가 우연히
  같았고, 원장 참조 추출은 TypeScript 원문에 있는 모든 `[4수...]`
  문자열을 구분 없이 수집했다. 진행 상태도 선택 단원이 바뀌는 경우를
  고려하지 않은 단일 `activeItemIndex`였다.
- 실패한 접근: 전역 기대값을 10에서 20으로만 바꾸면 한 단원에 문항을
  몰아도 통과한다. 선수 기준을 원장에서 `existing-reference`로 바꾸면
  구현하지 않은 내용을 출시했다고 거짓 기록하게 된다. 단원 전환 때
  전체 진행을 초기화하면 완료·복습 기록을 잃는다.
- 대응: 각 공개 단원을 독립적으로 10문항, K4/A4/R2, 추론 문제군 2개,
  표현 2개 이상인지 검사한다. 참조 추출은 `curriculumCode`와
  `curriculumCodes`가 선언된 줄만 읽고 `prerequisiteCodes`는 제외한다.
  단원이 실제로 달라질 때만 활성 문항을 0으로 돌리고 완료·복습·활동
  실행 기록은 보존한다. 영수증 콘텐츠 버전은 단원별로 선택한다.
- 확인: 계획 상태 원장 거부 테스트, 새 단원 1~9 전체 변형의 몫·나머지·
  역산·시험 몫 식, 단원별 분포, 선수 기준 비참조, 단원 전환 기록 보존,
  단원별 receipt 버전을 검사했다. 전체 421개 테스트, Grade 4와
  curriculum validator, mission audit, lint, TDD guard, build 75/75,
  E2E 40/40이 통과했다.
- 유지 계약: 4학년 단원을 추가할 때 전역 합계만 늘리지 않는다.
  각 단원의 교육과정 코드만 출시 참조로 세고 선수 기준은 학습 순서로만
  사용한다. 단원 전환은 현재 문항만 첫 위치로 되돌리며 과거 학습
  기록과 다른 학년 저장을 변경하지 않는다.

## 직육면체 그림과 전개도 선택지가 수학 구조를 충분히 반영하지 못함

- 증상: 직육면체 SVG는 가로·세로·높이 값이 달라도 같은 고정 좌표를
  사용했고, 역산 문항에서는 미지 길이를 가려도 좌표가 답의 비율을
  드러낼 수 있었다. 전개도 객관식은 보기 네 개 중 서로 같은 구조가
  반복되어 실제 접기 판단을 평가하지 못했다. 보강 중에는 A세트의 고정
  문장과 입력 문장이 일부 난수에서 같아져 세션 전체가 만들어지지 않는
  경우도 발견됐다.
- 원인: 직육면체의 투영 좌표가 치수 모델과 분리되어 있었고, 전개도
  보기는 정답 위치 라벨만 바꾸고 접기 가능한 구조를 검증하지 않았다.
  문제 생성기의 문장 중복 방지는 매개변수를 다시 뽑지만 고정 문장과
  매개변수 문장이 같은 결과가 되면 재시도만으로 해결할 수 없었다.
- 실패한 접근: 고정 SVG에 숫자 라벨만 붙이거나 보기 순서만 섞으면
  정량 그림과 접기 구조의 계약을 만족하지 못한다. 화면 전환 실패를
  초기 로딩 지연으로 보고 E2E 재시도 횟수만 늘리는 방식도 실제
  고유 문장 생성 실패를 숨긴다.
- 대응: 가로·세로·높이에서 사선 투영 벡터와 세 면의 polygon을 함께
  만들고 viewBox에 비례 축척한다. 미지 치수는 제출 전 중립값으로
  대체해 좌표와 라벨 모두에서 답을 가린다. 전개도는 2차원 칸을
  3차원 면 방향으로 접는 탐색으로 유효성을 판정하고, 정답 구조 하나와
  서로 다른 오답 구조 세 개를 결정적으로 배치한다. 충돌 가능한
  A세트 입력 문장은 고정 문장과 다른 맥락으로 바꾸고 A·B·C를
  0~199 시드에서 생성하는 회귀 검사를 추가했다.
- 확인: 모든 허용 직육면체 치수 조합의 비율·viewBox·미지값 마스킹,
  네 전개도 보기의 구조 중 정확히 하나만 접힘, 600개 세트 생성과
  문장 고유성을 검사했다. 전체 Vitest 61개 파일 416/416, lint,
  TDD guard, 이관 check, 템플릿 690/690, 문제 감사 오류·경고 0,

  역산 직육면체의 `?cm`, 네 전개도 구조, 가로 넘침 없음과 콘솔 오류
  0을 확인했다.
- 유지 계약: 직육면체 좌표·라벨은 같은 치수 모델에서 파생한다.
  `unknownMeasurement`는 제출 전 SVG 비율에도 답을 남기지 않는다.
  전개도 선택지는 DOM 구조가 네 개 모두 달라야 하고 정확히 하나만
  접을 수 있어야 한다. 템플릿 문장은 넓은 시드 범위에서도 세션 생성이
  실패하지 않아야 하며, 브라우저 초기화 실패를 재시도로 덮지 않는다.

## 합동이라고 표시한 두 SVG가 실제로는 서로 다른 도형임

- 증상: `congruence-001`은 두 사각형을 합동이라고 설명했지만 왼쪽과
  오른쪽 SVG의 대응변 길이가 달랐다. 직사각형 둘레·넓이 문항도 화면에는
  불규칙한 사각형을 그렸고, 일반 사각형의 `a`, `b`, `c` 라벨은 고정
  좌표의 실제 변 비율과 무관했다.
- 원인: 두 polygon 좌표를 독립된 문자열로 손으로 작성하고 수치 라벨만
  템플릿 매개변수에서 가져왔다. 문장·solver·라벨은 합동을 전제로 했지만
  도형 위상과 비율은 같은 수학 모델을 사용하지 않았다.
- 실패한 접근: 두 고정 SVG를 눈으로 비슷하게 다듬거나 오른쪽 도형의
  좌표만 한 번 맞추면 다른 치수 조합과 직사각형 문항에서 같은 모순이
  남는다. 합동·직사각형이라는 접근성 이름만 바꾸는 것도 정량 오류를
  해결하지 못한다.
- 대응: `a`, `b`, `c`를 첫 사각형의 연속한 세 변으로 갖는 모델을 만들고
  viewBox 안에 비례 축척한다. 직사각형은 같은 `a`, `b`에서 네 꼭짓점을
  만든다. 둘째 도형은 첫 도형의 각 꼭짓점을 정확히 90° 회전한 결과만
  사용해 모든 점 사이 거리와 대응 순서를 보존한다. 둘레·넓이 문항은
  `shape: rectangle`을 명시한다.
- 확인: 생성 범위를 덮는 1,331개 `a`·`b`·`c` 조합에서 세 변 비율,
  대응변 길이, 모든 꼭짓점의 viewBox 경계를 전수 검사했다. 브라우저
  E2E는 실제 SVG polygon 두 개의 모든 점 사이 거리가 같은지와 세 변
  비율을 다시 확인한다. 390×844 실제 화면에서 일반 사각형과 직사각형의
  라벨·가로 넘침·콘솔 오류를 확인했다.
- 유지 계약: 합동 도형을 독립 좌표로 두 번 그리지 않는다. 한 도형과
  강체 변환 하나에서 모든 대응점을 파생하며, 수치 라벨이 있으면 같은
  모델의 실제 변 길이 비율을 사용한다. 직사각형 맥락은 실제 직사각형을
  렌더링하고 접근성 이름도 같은 모양을 말해야 한다.

## 다각형 라벨은 맞지만 SVG 비율과 문제에 나온 도형이 다름

- 증상: `polygonarea-001`의 한 문항은 삼각형과 평행사변형의 넓이 합을 물으면서 삼각형만 그렸고, 다른 문항은 직사각형에서 삼각형을 잘라냈다고 하면서 온전한 직사각형만 그렸다. 공용 polygon SVG는 14×3과 6×5 직사각형도 같은 고정 좌표에 그렸다. 삼각형 둘레의 세 변도 독립 범위라 일부 조합에서 두 변의 합이 나머지 한 변보다 작았다.
- 원인: 문제 문장·solver·라벨은 매개변수를 공유했지만 도형 위상과 좌표는 `shape`별 고정 SVG였다. 한 polygon visual이 복합 도형을 표현할 수 없는데도 문항이 두 도형 또는 잘라낸 도형으로 확장됐다. 세 변 범위는 각 길이의 양수만 검사하고 삼각형 부등식을 구조적으로 보장하지 않았다.
- 실패한 접근: 라벨 숫자만 같은 모델에서 만들면 정량 그림 계약을 충족하지 못한다. 단일 도형 그림 아래 복합 도형 문장을 유지하면 학습자가 그림을 이용할수록 잘못된 모델을 보게 된다. 오류 분석 초안에서 넓이(cm²) 수치와 둘레(cm) 수치를 빼려 한 방식은 단위가 다른 양을 비교하는 차원 오류라 전수 검토 중 폐기했다.
- 대응: 복합 그림이 필요한 두 문항은 같은 삼각형 두 장의 전체 넓이와 단일 삼각형·사다리꼴의 공식 오류 분석으로 교체했다. 삼각형 세 번째 변은 `a+b-2`, 삼각형·사다리꼴의 넓이는 짝수 밑변 또는 높이에서 파생해 모든 조합의 위상과 정수 답을 보장했다. polygon renderer는 직사각형·정사각형·평행사변형·삼각형·사다리꼴·마름모의 실제 치수에서 좌표를 만들고 viewBox에 비례 축척한다. 역문제는 제출 전 미지 치수를 중립값으로 바꾸어 좌표와 라벨에서 가리고 제출 후 실제 비율을 사용한다.
- 확인: 생성기와 6개 기하 JSON의 바이트 재현성, 둘레·다각형 넓이 1,986개 허용 조합, 직사각형 두 비율, 삼각형 세 변 비율, viewBox 경계, 미지 치수 제출 전·후 쌍 테스트를 통과했다. 390×844에서 정사각형·미지 가로 직사각형·9×2 평행사변형·7/10×4 사다리꼴·8×6 삼각형을 직접 확인했다. 전체 406개 테스트, lint, TDD guard, 템플릿 690/690, 감사 오류 0·경고 8, build 75/75, E2E 37/37이 통과했다.
- 유지 계약: 정량 polygon은 치수에서 도형 위상·비율·라벨을 함께 파생한다. 복합 도형을 표현할 수 없는 visual로 복합 문항을 만들지 않는다. 세 변은 삼각형 부등식을, 면적 모델은 양의 길이와 필요한 정수성을 모든 허용 조합에서 보장한다. `unknownMeasurement` 값은 제출 전 텍스트뿐 아니라 SVG 좌표에도 반영하지 않는다. 생성 명령은 범위 밖 기하 은행을 재포맷하지 않아야 한다.

## 규칙과 대응 문항 수가 충분해도 구조가 반복되고 난이도가 역전됨

- 증상: `pattern-001`은 30문항이 있었지만 A/B/C가 같은 10개 구조를 반복해 문제군이 7개뿐이었고 K3/A15/R12로 치우쳤다. 첫 보강본은 K12/A12/R6과 문제군 10개를 충족했지만 난이도 신호가 6.14 > 5.50 < 6.36으로 역전됐다. 대표 문장에는 숫자 뒤 조사가 어색한 표현과 타일 수가 누적 증가로도 읽히는 문장도 있었다.
- 원인: 기존 은행은 대응 규칙을 추론하는 직접 문항을 과도하게 Reasoning으로 분류했고 숫자 범위만 바꿨다. 첫 보강본의 생활 맥락은 수학적으로는 Applying이었지만 문제 문장에 두 양의 대응 관계가 드러나지 않아 자동 난이도 신호가 낮았다. 숫자 매개변수 뒤 고정 조사는 값에 따라 달라지는 한국어 발음을 고려하지 못했다.
- 실패한 접근: 청사진 이름만 K/A/R로 재분류하면 실제 사고와 문제군 중복은 남는다. 자동 감사 수치를 맞추기 위해 숫자만 키우거나 맥락 키워드만 덧붙이면 교육적 의미가 불분명해진다. “단계마다 늘어나는 수”와 “한 단계에서 쓰는 수”를 섞으면 같은 solver라도 문장이 다른 수학을 뜻한다.
- 대응: 직접 적용 3종과 곱셈 역산 1종, 같은 묶음·고정량과 반복량·혼합 규칙 역산·묶음 안 계산 Applying 4종, 두 규칙 비교와 곱셈/덧셈 오류 분석 Reasoning 2종으로 다시 설계했다. 생활 문항은 두 양의 대응 관계를 명시하고 A/B/C의 수 기계·대응표·식과 맥락을 분리했다. 비교 답 `t-d`와 오류 차 `k*t-(t+k)`가 항상 양수가 되도록 `t` 범위를 `d`보다 크게 제한했다. 숫자 뒤 조사는 “배”, “만큼”, 식 표현으로 바꿨다.
- 확인: 생성기와 커밋 JSON의 완전 일치, 494개 허용 조합의 양의 정수 답·객관식 보기 4개·정답 1개·미평가 표현식 부재, 대표 30문장과 풀이를 확인했다. 전체 404개 테스트, lint, TDD guard, migration check, 690/690 템플릿, 감사 오류 0·경고 12, 난이도 6.09 < 7.10 < 8.47, 정적 페이지 75/75가 통과했다.
- 유지 계약: 규칙과 대응은 A/B/C별 K4/A4/R2, 문제군 10개, 추론 문제군 2개를 유지한다. 역산은 정수가 되도록 정방향 모델에서 출력값을 만들고, 비교·오류 답은 모든 허용 조합에서 양수여야 한다. 숫자 매개변수 바로 뒤에 값에 따라 달라지는 조사를 붙이지 않으며, 생활 문장의 대응 관계와 solver가 같은 수학을 뜻하는지 대표 렌더링으로 확인한다.

## 청사진 100%가 응용문제 품질 완료를 뜻하지 않음

- 증상: 5학년 660개 템플릿이 모두 유효한 청사진을 가졌지만 반올림, 올림·버림, 자연수 혼합 계산의 각 30문항은 K30/A0/R0이었고 소수의 곱셈은 K27/A3/R0이었다. 평균도 K18/A12/R0, 분수의 곱셈은 K21/A9/R0이었고 두 은행 모두 문제군이 5개 이하였다. 반올림과 올림·버림은 직접 계산 문제군을, 혼합 계산과 소수의 곱셈은 숫자 범위만 달라진 같은 계산식을 A/B/C에서 반복했고 평균은 임의의 수를 `avg3`로 반올림하는 구조까지 포함했다. 분수의 곱셈 단원 설명에 있는 분수×자연수도 실제 문제은행에는 없었다. metadata 100%만 보면 이 공백이 가려졌다.
- 원인: 초기 이관은 기존 의미를 정직하게 분류하는 작업이었으며 부족한 Applying·Reasoning 문제를 새로 만드는 단계가 아니었다. 숫자 범위와 문장 배경만 바꾼 슬롯을 새 문제군으로 세지 않은 결과가 품질 감사 경고로 남아 있었다.
- 실패한 접근: 기존 직접 계산 문항에 `applying`이나 `reasoning` 이름만 붙이면 감사 수치는 줄지만 학습자가 수행하는 사고는 변하지 않는다. 난이도 3에 고정 답이 작은 추론 문제만 넣으면 K/A/R은 맞아도 자동 난이도 신호가 역전될 수 있다.
- 대응: 여섯 개념을 각각 독립 단위로 잡아 A/B/C 각 세트를 K4/A4/R2로 다시 작성했다. 반올림은 합·차, 가능한 범위 역산, 경계 확인, 계산 순서 비교로 확장했다. 올림·버림은 부족하지 않은 위 경계와 완성 가능한 아래 경계를 실제 좌석·묶음 상황에서 선택하고, 잘못된 방향의 어림이 만드는 부족량을 분석하게 했다. 혼합 계산은 재고·두 모둠·꾸러미·모둠별 남은 수를 식으로 옮기고, 괄호를 빠뜨린 식과 올바른 모델의 차이를 분석하게 했다. 소수의 곱셈은 반복량·합친 양·넓이·남은 양을 모델링하고, 소수점을 빠뜨린 오답과 한 인수가 10분의 1이 될 때 곱의 변화를 비교하게 했다. 평균은 대칭 수로 정확히 나누어지는 자료를 만들고, 실제 맥락·빠진 값·목표 평균 역산·잘못된 자료 수·기록 수정의 평균 영향을 다루게 했다. 분수의 곱셈은 분수×자연수, 분수×분수, 곱셈 전 약분, 실제 양의 일부, 일부의 일부, 빠진 인수, 분수 변의 넓이, 분모 누락 오류와 곱의 크기 비교를 다룬다. 정답식은 풀이에서 설명한 상황과 방법 차이를 그대로 계산하며 개념별 결정적 생성 스크립트가 JSON을 재현한다.
- 확인: 각 개념에서 먼저 부족한 분포를 드러내는 실패 테스트를 실행한 뒤 K12/A12/R6, 문제군 10개, 추론 문제군 2개, A/B/C별 K4/A4/R2, 생성기와 JSON 완전 일치를 검사했다. 분수의 곱셈 보강 뒤 5,112개 허용 조합에서 기약분수 정답, 객관식 보기 4개와 정답 1개, 미평가 표현식 부재를 전수 검사했고 전체 400개 테스트, lint, TDD guard, 이관 check, 템플릿 검증, 문제 감사, 정적 build가 통과했다. 문제 감사 경고는 41개에서 37개로 줄었다. 난이도 신호는 반올림 11.12 < 11.48 < 13.90, 올림·버림 10.68 < 11.35 < 13.69, 혼합 계산 6.93 < 7.36 < 9.21, 소수의 곱셈 5.03 < 6.31 < 9.10, 평균 5.70 < 6.31 < 7.73, 분수의 곱셈 6.31 < 8.33 < 9.74다.
- 유지 계약: 청사진 complete와 콘텐츠 커버리지 pass를 구분한다. 응용문제 보강은 metadata 재분류로 처리하지 않고 문장·매개변수·solver·풀이·힌트를 함께 검토한다. 새 생성기는 커밋된 JSON과 완전히 같아야 하며 한 개념의 감사 경고를 없애면서 새 난이도·정답·중복 경고를 만들면 완료가 아니다.

## 좁은 3열 버튼은 한글 단어를 음절 사이에서 끊음

- 증상: 390px 6학년 개념 화면에서 `세트 A · 5문제`가 세 줄로
  밀리며 `5문 제`처럼 단어 안에서 줄바꿈됐다. 터치 영역과 동반자
  비겹침은 통과했지만 어린이가 한눈에 세트와 문제 수를 읽기 어려웠다.
- 원인: Grade 6 하단 행동은 동반자 안전 영역을 제외한 폭에 버튼
  세 개를 배치하면서 공용 큰 버튼의 넓은 좌우 padding과 자동
  word-break를 그대로 사용했다.
- 실패한 접근: 버튼 전체 문장을 `nowrap`으로만 바꾸면 약 96px 버튼에

- 대응: 접근성 이름은 `세트 A · 5문제`로 유지하되 보이는 문장은

- 확인: 실패 E2E가 줄 요소 부재를 먼저 잡았고 수정 뒤 390×844와

  실화면에서 `5문제`와 `10문제`가 단어 단위로 보이고 가로 넘침과

- 유지 계약: 좁은 한글 행동 문구는 임의 음절 줄바꿈에 맡기지 않는다.

## 소수 나눗셈을 임의 수 범위로 만들면 반복소수와 표시 오차가 섞임

- 증상: 소수 나눗셈 템플릿에서 임의의 자연수·소수 조합을 사용하면
  몫이 반복소수가 되거나 이진 부동소수점 표시 찌꺼기가 정답 문자열에
  들어갈 수 있다. 첫 청사진에는 허용 목록에 없는 `place_value`
  reasoning pattern도 들어가 집중 검증이 실패했다.
- 원인: 성취기준이 소수 몫을 요구한다고 해서 모든 나눗셈이 현재의
  유한 숫자 입력·정답 계약에 맞는 것은 아니다. 또한 자릿값이라는
  수학 내용과 reasoning pattern의 정해진 식별자를 혼동했다.
- 실패한 접근: 몫을 임의 자리에서 반올림하면 문제에 제시하지 않은
  근삿값 규칙이 채점에 섞인다. 새 pattern 이름을 즉석에서 만들면
  여러 은행을 비교하는 청사진 계약이 깨진다.
- 대응: 나누는 수를 2·4·5·10·20·25·50·100 또는
  0.1·0.2·0.25·0.3·0.5로 제한하고, 나누어지는 수를 같은 정수
  tenths·hundredths 모델에서 만들어 모든 몫이 유한소수가 되게 했다.
  자릿값 이동 문항은 기존 `representation_shift` pattern으로
  분류했다.
- 확인: 생성기와 JSON 바이트 일치, 180개 허용 매개변수 조합의 정수·
  유한소수 답과 완전 렌더링, 세트별 K/A/R 4/4/2, 문제군 30개,
  두 성취기준 매핑을 검사했다. 전체 Vitest 490/490, 두 감사
  오류·경고 0, build 84/84, 전체 E2E 56/56과 390×844 실화면을
  통과했다.
- 유지 계약: 소수 나눗셈은 문제에 명시하지 않은 반올림을 도입하지
  않는다. prompt·solver·풀이를 하나의 정수 tenths/hundredths 모델에서
  만들고 모든 허용 매개변수의 답 문자열을 전수 검사한다. reasoning
  pattern은 중앙 허용 목록 안에서만 선택한다.

## 비례식 오류 분석의 위치 표현과 작은 답이 품질 신호를 왜곡함

- 증상: 첫 비례식 은행은 수학적 답과 분포 검증을 통과했지만 품질
  감사에서 “두 번째 항”을 분수의 위치 피연산자로 오인한 경고 4개와
  difficulty 2 평균 5.10보다 낮은 difficulty 3 평균 4.38 경고가 났다.
- 원인: 공용 숨은 분수 검사는 “첫 번째/두 번째”와 “항”의 조합을
  모호한 분수 연산 참조로 본다. 비례배분 오류의 답은 누락한 한 부분
  `p`라 작아서, 실제 오류 분석을 하더라도 숫자 크기만으로는 난이도가
  충분히 드러나지 않았다.
- 실패한 접근: 감사 예외를 비례식 개념 전체에 추가하면 실제로 기준
  피연산자를 빠뜨린 문장도 통과한다. `p` 범위만 키우면 문제의 사고
  과정은 그대로이고 자동 수치만 맞춘다.
- 대응: 모호한 서수 표현을 “비의 뒷항”으로 바꾸고, Reasoning 문항이
  수행하는 배수 규칙 검산과 비례배분 규칙 계산을 prompt에 명시했다.
  정답식이나 수 범위는 품질 수치 때문에 바꾸지 않았다.
- 확인: 재생성 뒤 감사 오류·경고 0, 난이도 4.79 < 5.10 < 5.48,
  문제군 30개와 추론 문제군 6개를 확인했다. 전체 Vitest 496/496,
  build 87/87, 전체 E2E 57/57과 390×844 실화면을 통과했다.
- 유지 계약: 비례식 위치는 실제 항을 문장이나 식에 명시하고 모호한
  “첫 번째/두 번째”만 쓰지 않는다. 추론 난이도는 답 크기를 키우는
  대신 학습자가 검산·비교하는 사고를 prompt와 풀이에 드러낸다.

## iPad에서 풀이장 대신 주변 글자가 선택됨

- 증상: iPadOS Safari·Chrome에서 펜이나 손가락 입력이 간헐적으로 시작되지 않고 캔버스 아래 `단계 힌트` 글자가 선택된다.
- 원인: 캔버스만 선택 불가로 만들어도 WebKit은 같은 상호작용 영역의 선택 가능한 형제 글자를 선택 대상으로 삼는다. React 포인터 이벤트의 기본 동작 취소만으로 네이티브 선택 경로가 항상 막히지도 않는다.
- 대응: 연습 화면 전체의 `practice-interaction-surface`와 자손에 WebKit 선택·콜아웃 차단을 유지하고 `input`, `textarea`만 선택을 다시 허용한다. 캔버스의 pointer·touch 시작과 이동은 캡처 단계의 non-passive 네이티브 리스너에서 취소한다. 한 `pointerId`만 처리하고 시작점을 즉시 그리며 빠른 입력은 coalesced event를 순서대로 그린다. `setPointerCapture()` 실패는 스트로크 실패로 취급하지 않는다.
- 확인: 컴포넌트 테스트 뒤 WebKit에서 힌트의 `webkitUserSelect`, 빈 `window.getSelection()`, 취소된 `touchstart`, 실제 캔버스 픽셀을 확인하고 마지막에는 실제 iPad에서 검증한다.

## 개발 서버와 빌드가 서로 방해함

- 증상: 개발 서버가 켜진 채 `next build`를 실행하거나 반대로 실행하면 `.next` 관련 오류, 사라진 산출물, 일관되지 않은 화면이 나타난다.

- 대응: 개발 서버를 종료한 뒤 빌드한다. 브라우저 확인이 계속 필요하면 완성된 `out/`을 별도 HTTP 서버로 제공한다.
- 확인: 남은 Next 프로세스가 없는 상태에서 빌드를 다시 실행하고 정적 경로 수와 종료 코드를 확인한다.

## GitHub Pages 경로에서는 루트 기준 자산이 깨짐

- 증상: 로컬 루트에서는 JSON과 이미지가 보이지만 실제 `/math_assist` 배포에서는 404가 난다.
- 원인: 배포본은 도메인 루트가 아니라 `basePath` 아래에 있으며 정적 데이터와 자산 URL이 접두 경로를 빠뜨렸다.

- 확인: 로컬 E2E의 `/math_assist` 기준 경로와 배포된 새 브라우저 세션에서 모두 자산 응답과 렌더 화면을 확인한다.

## 정적 HTML 응답만으로 화면 성공을 판단할 수 없음

- 증상: 정적 경로의 HTTP 응답은 성공하지만 저장 기록에 따른 이어하기, 클라이언트 오류, 실제 버튼 상태가 확인되지 않는다.
- 원인: 홈·연습·결과의 주요 상태는 브라우저 hydration과 localStorage를 읽은 뒤 결정된다.
- 대응: 경로 존재는 정적 산출물로 확인하고, 상태 기반 동작은 Playwright나 실제 브라우저에서 확인한다.
- 확인: 새 브라우저와 기록을 주입한 브라우저를 나누어 주요 행동, 콘솔 오류, 저장 변경을 검사한다.

## 이전 진도 형식을 읽을 때 최신 형식으로 덮어쓰면 기록이 손상됨

- 증상: 홈만 방문했는데 예전 완료·복습·선택 단원 기록이 줄거나 다른 형식으로 바뀐다.
- 원인: 홈은 1·2·3·5학년의 서로 다른 저장 형식을 요약할 뿐 소유하지 않는데, 읽기 과정에서 정규화 결과를 다시 쓰면 학년별 마이그레이션 책임이 섞인다.
- 대응: `guest-home`은 기존 이름을 읽기만 하고 `mathAssist_guestHome_v1`에는 선택 학년만 저장한다. 학년별 형식 변경은 해당 진행 모듈의 로더·저장기와 이전 형식 회귀 테스트에서 수행한다.
- 확인: 각 과거 저장 예제를 넣고 홈을 연 뒤 기존 키의 원문이 변하지 않았는지와 이어하기 대상이 맞는지 확인한다.

## 템플릿 수정이 열려 있는 연습에 반영되지 않음

- 증상: JSON 템플릿을 고쳤는데 이미 시작한 문제는 이전 문장·정답·그림을 계속 사용한다.
- 원인: 세션을 만들 때 생성된 문제 전체를 localStorage에 스냅샷으로 저장한다.
- 대응: 검증할 때 기존 활성 세션을 명시적으로 지우거나 새 세트·개념으로 시작한다. 제품에서는 진행 중 세션의 정답을 조용히 바꾸지 않는다.
- 확인: 새 세션의 `templateId`, 문장, 정답, 시각 데이터가 변경본에서 생성됐는지 확인한다.

## 정답 선노출은 보이는 글자만 가려서는 남음

- 증상: 문제 화면에서 결과 숫자를 가렸지만 다른 시각 유형이나 접근성 이름에 정답이 남는다.
- 원인: `visualConfig`의 `result`, `target`, `product` 같은 답 전용 필드를 렌더러가 제각각 해석한다.
- 대응: 문제 카드의 공개 상태를 모든 시각 렌더러에 전달하고, 공개 전에는 답 전용 값이 DOM에 생성되지 않게 한다.
- 확인: 렌더러 집중 테스트와 브라우저 E2E에서 제출 전 부재와 제출 후 존재를 한 쌍으로 검사한다.

## E2E 동시 실행에서 일회성 시간 초과가 발생함

- 증상: 2026-07-21 전체 17개 브라우저 테스트의 첫 실행에서 한 테스트가 숫자 키패드를 기다리다 30초에 종료됐지만, 같은 테스트 단독 실행과 전체 재실행은 코드 변경 없이 통과했다.
- 원인: 재현되지 않아 확정하지 못했다. 여러 작업자가 개발 서버를 시작하는 전체 실행의 초기 로딩 경쟁이 후보지만 증거는 없다.
- 대응: 같은 실패가 다시 나면 실패 영상·추적에서 실제 문제 유형과 페이지 상태를 먼저 확인하고, 무조건 재시도 횟수만 늘리지 않는다.
- 확인: 실패 테스트 단독 실행 뒤 전체 17개를 같은 설정으로 다시 실행해 단독·전체 결과를 함께 기록한다.

## 세 도형 겹침 그림의 고정 SVG가 문제 수치와 모순됨

- 증상: `triple-overlap-inclusion` 예시에서 계산상 `BC만` 영역은 0인데 고정 다각형 SVG에는 B와 C만 겹친 영역이 보였다. 단독 영역의 시각 비율도 문제 수치와 크게 달랐다.
- 원인: 문제 문장과 정답은 `shapeArea`, `exclusiveAreas`, `tripleOverlap`에서 계산했지만 그림은 이 값과 무관한 세 다각형 좌표를 사용했다. 고정 좌표를 조금 조정하는 접근은 다른 매개변수에서 같은 오류를 반복하며, 이중 겹침값을 직접 라벨링하면 중간 답을 선노출한다.
- 대응: 세 도형의 공통 넓이 식을 풀어 `A만`, `B만`, `C만`, `AB만`, `AC만`, `BC만`, `ABC`의 일곱 영역 모델을 만든다. 새 문제는 이 모델을 저장하고, 구형 세션은 렌더 시 같은 함수로 모델을 복원한다. SVG는 한 칸 1단위 넓이의 같은 크기 셀을 그려 비율을 정확히 보존하고, 0인 영역은 DOM에 만들지 않는다. 문제에서 주지 않은 이중 겹침값은 숫자 라벨로 표시하지 않는다.
- 확인: 모델 단위 테스트에서 각 도형 넓이 재구성, 음수·비정수 거부, 합집합 넓이를 검사한다. 렌더러는 영역별 셀 수, 0 영역 부재, 중간 답 라벨 부재를 검사한다. 템플릿 검증기는 모든 파라미터 표본의 가능성을 검사하며, E2E는 새 payload와 `model`·`semantics`가 없는 구형 저장 세션을 모두 확인한다. 모바일 390×844와 태블릿 1024×768에서 가로 넘침과 콘솔 오류가 없어야 한다.

## 문제 템플릿 산술을 허용 문자 검사 뒤 `eval`로 실행함

- 증상: 숫자와 산술 기호만 남기는 정규식이 있었지만 문제 생성기가 템플릿 식을 `eval`로 실행해 엄격한 CSP와 정적 코드 검토에서 차단 요소가 됐다.
- 원인: 템플릿의 등록 함수 호출을 먼저 값으로 치환한 뒤 남은 산술식의 우선순위와 단항 부호를 처리할 작은 평가기가 없었다. 품질 감사의 임시 TypeScript 로더도 생성기의 직접 의존 파일을 수동으로 복사해 새 모듈 추가 시 검증 명령이 깨질 수 있었다.
- 대응: 유한 십진수, 괄호, `+ - * /`, 단항 부호만 해석하는 길이·중첩 제한 재귀 하강 parser를 별도 모듈로 둔다. 지수, 식별자, `NaN`, `Infinity`, 0 나눗셈, 후행 토큰, 비유한 결과는 거부한다. 생성기는 기존 등록 함수 처리 뒤 이 parser만 호출하고, 감사 로더는 parser 모듈도 같은 임시 디렉터리에 변환한다.
- 확인: parser 허용·거부 쌍 테스트, 등록 함수 인자 산술, 거부 식의 미평가 표식, 모든 5학년 템플릿의 A/B/C 10문제 결정론 생성, 6학년 5/10문제 생성, `validate:templates`, `validate:grade6`, `audit:problems`을 함께 실행한다.

## 연습 초기화가 같은 요청의 무작위 세션을 두 번 생성함

- 증상: 세 도형 겹침 E2E를 병렬 반복하면 localStorage에서 찾은 겹침 문제 인덱스를 눌렀는데 화면에는 같은 인덱스의 다른 넓이 문제가 나타났다. 수정 전 재현은 10회 중 2회 실패했으며, 더 단순한 단독 실행은 통과해 문제를 숨겼다.
- 원인: React Strict Mode의 개발용 mount-cleanup-remount가 비동기 초기화 effect를 두 번 시작했다. cleanup 뒤에도 첫 실행이 `await`에서 돌아와 별도의 무작위 문제 묶음을 저장했고, 브라우저 검사가 첫 저장을 읽은 직후 두 번째 실행이 저장과 화면 상태를 교체할 수 있었다. 병렬 개발 서버 부하는 이 창을 넓혔지만 원인은 서버 간 저장 공유가 아니라 한 탭 안의 stale effect였다.
- 대응: effect 실행마다 활성 플래그를 두고 release gate, 개념, 템플릿의 각 비동기 경계 뒤에 현재 실행인지 확인한다. cleanup된 실행은 localStorage, 화면 세션, 차단 상태, 오류, 로딩 상태를 변경하지 않는다. 기존 `saveSession`을 그대로 사용하므로 5·6학년 분리와 손상 저장소 덮어쓰기 거부 계약은 유지된다.
- 확인: Strict Mode 컴포넌트 테스트에서 개념 조회는 두 번 시작되더라도 템플릿 생성·세션 저장·화면 반영은 활성 실행 한 번만 수행되는지 확인한다. 실제 겹침 E2E는 재시도 없이 6 workers로 10회 이상 반복하며 저장 스냅샷으로 고른 문제가 화면에도 나타나는지 확인한다.
- 유지 계약: 새 `await`를 초기화 effect에 추가할 때는 그 결과로 상태나 저장소를 바꾸기 전에 활성 실행 여부를 확인한다. 취소된 실행의 `finally`도 로딩 상태를 끝내면 안 되며, 불안정성을 재시도 횟수 증가나 테스트 대기로 가리지 않는다.

  2평행쌍, 마름모 4같은 변·2평행쌍을 검사했다. 390×844 실제
  Chromium에서 299px 모형, 표식 수, 375px 문서 폭, 콘솔 오류
  0을 확인했다. 한 각만 주어진 평행사변형 문항은 추론 결과인 나머지
  세 직각 표식을 만들지 않는 제출 전 DOM 테스트도 통과했다.
- 유지 계약: 사각형 문제·정답·풀이·꼭짓점·성질 표식은 하나의
  속성 모델을 사용한다. 도형 이름은 그림 자체에 넣지 않으며,
  정사각형이 직사각형과 마름모의 성질을 함께 가진다는 문항과
  불충분한 조건의 반례를 유지한다. 새 변형은 390px 실화면에서
  표식이 변 위에 있고 답 선택을 가리지 않는지 확인한다.

## 모양 채우기 그림이 떨어져 있으면 빈틈의 수학을 보여 주지 못함

- 증상: 첫 정오각형 추론 그림은 세 도형과 가운데 빈틈을 각각
  표시했지만 정오각형끼리 변을 공유하지 않고 떨어져 있어 “변끼리
  이어 놓았다”는 문제 문장과 맞지 않았다.
- 원인: 각 정오각형을 독립된 중심 좌표에 배치하고 중앙에 고정
  빈틈 도형을 얹었다. 도형 수는 맞았지만 한 점에 모이는 정오각형
  내각과 공유 변의 위상을 모델링하지 않았다.
- 실패한 접근: 떨어진 정오각형 사이에 빈틈 색만 더 크게 표시해도
  모든 틈이 의도된 36° 빈틈처럼 보이므로 수학적 의미가 회복되지
  않는다. 변형에 따라 네 개를 놓으면 정오각형 내각의 합이 360°를
  넘어 겹치므로 “항상 빈틈”이라는 설명도 틀린다.
- 대응: 세 정오각형을 하나의 꼭짓점에서 시작해 각 변을 같은
  길이로 걷고 바깥각 72°만큼 회전해 좌표를 만든다. 다음 도형은
  108° 뒤에서 시작해 앞 도형의 마지막 변을 공유한다. 세 내각이
  324°를 차지한 뒤 남는 36° 쐐기만 빈틈으로 표시한다. 변형은
  도형 수가 아니라 문제에 주어진 공통 변 길이를 바꾼다.
- 확인: 모든 변형에서 정오각형 수 3, 공통 시작 꼭짓점, `hasGap`,
  행·열에서 파생한 타일 수와 답, 인접 삼각형 두 꼭짓점의 완전한
  공유 변을 검사했다. 390×844 실제
  Chromium에서 공유 변과 주황색 36° 빈틈, 299px 모형, 375px 문서
  폭, 새 콘솔 오류 0을 확인했다.
- 유지 계약: 모양 채우기 그림은 문제의 타일 수뿐 아니라 공유 변,
  겹침, 빈틈의 위상을 표현한다. 정오각형 추론은 세 개와 36° 빈틈을
  유지하며, 타일 수나 빈틈을 고정 장식으로 따로 그리지 않는다.

## 각도 그림을 장식으로 그리면 눈금·광선·내각 답이 서로 어긋남

- 증상: 각도 측정 문제를 고정 각도기 그림으로 만들면 문장의 각도와
  광선이 가리키는 눈금이 달라질 수 있다. 내각 문제에서 미지각 값을
  시각 설정이나 라벨에 그대로 넣으면 제출 전에 답이 노출될 수 있다.
- 원인: 문제 수치, 정답, 풀이, SVG 좌표를 서로 독립적으로 정하면
  변형마다 같은 수학을 유지할 공통 모델이 없다. 특히 평행사변형은
  맞은편의 알려진 각이 미지각과 같은 값일 수 있어, 정답 문자열이
  그림 전체에 없다는 검사만으로는 선노출 여부를 올바르게 판정할 수
  없다.
- 실패한 접근: 광선을 눈대중으로 고정 눈금 위에 놓고 텍스트 답만
  숨기면 좌표 불일치는 남는다. 반대로 미지각과 같은 숫자가 SVG
  어디에도 없다고 단정하면, 평행사변형의 합법적인 알려진 반대각까지
  제거하게 된다.
- 대응: 하나의 각도 값에서 각도기 눈금과 광선 끝점을 삼각함수로
  계산한다. 삼각형과 평행사변형은 주어진 내각에서 꼭짓점과 남은
  내각을 계산하되, 숨긴 꼭짓점에는 숫자 대신 `□`만 만든다. 선택지
  오답도 모든 변형에서 정답과 중복되지 않는 가까운 각도로 계산한다.
- 확인: 1~9 모든 변형에서 광선의 역산 각도, 삼각형 180°,
  사각형 360°, 선택지 네 개의 고유성과 단일 정답을 검사했다.
  390×844 실화면에서 각도기 299px, 문서 폭 375px, 광선 좌표와
  가로 넘침 0을 확인했다. 전체 Vitest 62개 파일 465/465, lint,
  TDD guard, 14단원·140문항 K/A/R 56/56/28 검증, curriculum
  현재 참조 62개, 두 감사 오류·경고 0, build 75/75, 단일 작업자
  전체 E2E 52/52가 통과했다.
- 유지 계약: 각도 문제·정답·풀이·눈금·광선·도형 꼭짓점은 같은
  각도 모델에서 파생한다. 미지각 노드는 제출 전 숫자를 가지지
  않으며, 정답 선노출 검사는 같은 값의 합법적인 알려진 각이 아니라
  미지 꼭짓점 노드와 접근성 텍스트를 대상으로 한다. 새 변형은 모든
  선택지가 고유하고 정답이 정확히 한 번만 포함되는지 검사한다.

## 꺾은선그래프를 고정 좌표로 그리면 표·눈금·변화량이 분리됨

- 증상: 자료 표와 그래프를 따로 작성하면 점의 높이와 표의 값이
  어긋나거나, 최대 변화 구간과 최댓값·최솟값의 차가 그림과 다른
  답을 만들 수 있다. 같은 자료의 눈금 범위 비교도 값까지 달라지면
  시각적 과장 효과를 설명할 수 없다.
- 원인: 시점, 원자료, 표시 자료, 세로축 범위를 하나의 모델로
  연결하지 않고 SVG 좌표를 고정하면 숫자 변형마다 독립된 사실이
  생긴다.
- 실패한 접근: 새 그래프 문제에 `g4-line-*` 접두사를 쓰자 기존
  수직·평행 단원의 안정 식별자와 충돌했다. 또한 그래프마다 자료의
  최솟값과 최댓값으로 축을 자동 축소하면, 같은 자료를 넓은 눈금과
  좁은 눈금으로 비교하는 추론 문항의 차이가 사라진다.
- 대응: 새 식별자를 `g4-graph-*`로 분리한다. 쉼표로 직렬화한
  시점·자료 배열과 명시적 `yMin`·`yMax`·`yStep`에서 모든 점과
  선분 좌표를 계산하고, 정확한 값 읽기 문항은 5단위 보조눈금을
  함께 그려 모든 점을 그 눈금에 맞춘다. 표 완성은 같은 배열에서 한 셀만 `□`로
  가리고, 오류 분석은 별도 원자료 배열과 표시 배열이 한 시점에서만
  다르게 한다. 눈금 비교는 자료 배열을 공유하고 축 범위만 바꾼다.
- 확인: 1~9 모든 변형에서 점 값, 최대 변화 구간, 범위, 빠진 표 값,
  단 하나의 오점, 축 범위와 보조눈금 정렬, 선택지 고유성과 단일
  정답을 검사했다. 390×844 실화면에서 그래프 299px, 점 5개·
  선분 4개·5단위 보조격자, 문서 폭 375px, 가로
  넘침 0을 확인했다. 전체 Vitest 62개 파일 469/469, lint, TDD
  guard, 15단원·150문항 K/A/R 60/60/30 검증, curriculum 현재
  참조 63개, 두 감사 오류·경고 0, build 75/75, 단일 작업자 전체
  E2E 53/53이 통과했다.
- 유지 계약: 시점·원자료·표·점·선분·눈금·풀이를 같은 자료 모델에서
  파생한다. 모든 값은 축 범위 안에 있어야 하며, 의도적 오류 문제는
  정확히 한 점만 원자료와 달라야 한다. 좁은 눈금과 넓은 눈금 비교는
  값 배열을 바꾸지 않는다. 새 그래프 문제는 `g4-graph-*` 식별자와
  최소 390px 실화면 검증을 유지한다.

## 쌓기나무 입체와 세 방향 그림을 따로 만들면 가려진 나무가 달라짐

- 증상: 쌓기나무 입체 그림, 전체 개수, 위·앞·옆에서 본 모양을 각각
  고정 데이터로 작성하면 한 방향에 가려진 나무를 빠뜨리거나 투영의
  높이가 실제 기둥과 달라질 수 있다. 투영의 정사각형 수를 전체
  쌓기나무 수로 답하는 오류도 그림만으로 검증하기 어렵다.
- 원인: 큐브 좌표와 정투영을 서로 다른 표현에서 만들면 어느 바닥
  자리에 몇 개가 쌓였는지 공유하는 수학 모델이 없다. 합계나 오류의
  차를 시각 설정에 넣으면 제출 전 DOM 또는 접근성 이름에 정답 전용
  값이 생길 위험도 있다.
- 실패한 접근: 입체 SVG와 세 투영 SVG를 눈대중으로 맞추거나, 보이는
  큐브 수를 전체 수로 간주하는 방식은 뒤에 가려진 기둥을 보존하지
  못한다. 고정 합계를 접근성 설명에 넣는 방식은 그림 검증에는
  편하지만 정답 선노출 계약을 깨므로 사용하지 않았다.
- 대응: 바닥의 각 자리를 0~6 높이로 나타낸 하나의 격자를 둔다.
  전체는 모든 높이의 합, 위 모양은 높이 1 이상 여부, 앞 모양은 각
  열의 최댓값, 옆 모양은 각 행의 최댓값으로 파생한다. 같은 격자에서
  등각 투영 큐브의 세 면과 세 방향 정사각형을 그리며 답 전용 합계는
  렌더러에 전달하지 않는다.
- 확인: `[[p,1],[2,0]]`의 모든 `p=2~5`에서 전체 `p+3`, 위 3칸,
  앞 `[p,1]`, 옆 `[p,2]`와 실제 큐브 수를 검사했다. 개념 시각도
  문제 카드와 같은 렌더러를 사용한다. 390×844 실제 화면에서
  쌓기나무 6개, 위 3칸·앞 4칸·옆 5칸, 10문항의 파생 요소 수,
  정답 메타데이터·가로 넘침·콘솔 오류 0을 확인했다.
- 유지 계약: 쌓기나무 문제·정답·풀이·입체 큐브·위·앞·옆 투영은
  하나의 높이 격자에서 파생한다. 시각 설정에는 `answer`, `result`,
  `target` 같은 답 전용 필드를 두지 않는다. 새 높이 격자는 2~3행과
  2~3열, 비음수 높이를 지키고 실제 큐브 수와 세 투영을 함께
  회귀 검사한다.

## 원의 길이·넓이 그림을 따로 만들면 반지름과 지름이 뒤바뀜

- 증상: 원주, 원의 넓이, 원주율 측정 그림을 각각 고정 값으로 만들면
  문장의 반지름과 그림의 지름이 어긋나거나 원주÷지름이 3.14가 아닌
  값이 될 수 있다. 원형 고리도 안쪽·바깥쪽 넓이가 같은 원에서
  파생되지 않으면 칠한 영역과 답이 달라진다.
- 원인: 반지름, 지름, 원주, 넓이와 SVG 반지름을 독립적으로 입력하면
  이 값들을 묶는 공통 원 모델이 없다. 정답인 원주나 넓이를 편의를
  위해 시각 설정에 넣으면 제출 전 DOM이나 접근성 이름으로 새어
  나갈 위험도 있다.
- 실패한 접근: 모든 원에 원주와 넓이 라벨을 함께 표시하면 원주율
  측정 문제는 설명하기 쉽지만 계산 문제의 답을 선노출한다. 반복
  응용을 숫자 라벨만 붙인 원 하나로 나타내면 실제 반복 수를 확인할
  수 없고, 고리는 두 원을 고정 반지름으로 그리면 두께 비율이 수치와
  달라진다.
- 대응: 반지름, 원주율, 반복 수와 선택적 안쪽 반지름을 입력으로
  지름·원주·넓이를 계산한다. 원주율 문항에서만 측정 원주와 지름을
  주어진 값으로 표시하고, 원주·넓이 문항은 필요한 반지름 또는
  지름만 표시한다. 반복 원은 실제 개수만큼 그리고 고리의 안쪽
  반지름 비율을 바깥 원에 맞춰 그린다.
- 확인: 반지름 2~6에서 지름 `2r`, 원주 `2×3.14×r`, 넓이
  `3.14×r²`를 검사했다. 390×844 실제 화면에서 지름 10cm·측정
  원주 31.4cm, 반복 원 2개, 바깥 4cm·안쪽 3cm 고리, 가로 넘침·
  정답 메타데이터·콘솔 오류 0을 확인했다.
- 유지 계약: 원 문제·정답·풀이·지름·원주·넓이·SVG 반지름은 같은
  원 모델에서 파생한다. `focus=pi`가 아닌 제출 전 그림에는 계산
  결과인 원주나 넓이를 표시하지 않는다. 안쪽 반지름은 바깥 반지름
  보다 작아야 하고 반복 수 1~4를 실제 원 요소 수로 회귀 검사한다.

## 직육면체의 면·채움·미지 길이를 따로 그리면 수치 모델이 갈라짐

- 증상: 겉넓이 그림, 부피 그림, 뚜껑 없는 상자와 부분 채움 그림을
  각각 고정 SVG로 만들면 같은 가로·세로·높이인데도 면의 비율이나
  수면 높이가 달라질 수 있다. 역산 문제의 정답 높이를 좌표 계산에
  그대로 쓰면 라벨만 가려도 그림 비율에서 답이 드러난다.
- 원인: 세 길이와 투영 좌표, 세 면, 채움 높이, 미지 길이 마스킹을
  하나의 모델로 묶지 않으면 문제·정답·그림이 각자 다른 값을
  사용하게 된다.
- 실패한 접근: 정면 직사각형 하나만 표시하면 세 길이를 구별할 수
  없고, 열린 상자의 윗면을 단순 삭제하면 어떤 면이 빠졌는지
  불분명하다. 실제 정답 높이로 직육면체를 그린 뒤 `?cm`만 붙이는
  방식도 도형의 비율로 역산 답을 노출한다.
- 대응: `cuboid`의 가로·세로·높이에서 앞·옆·윗면과 좌표를 함께
  파생한다. 열린 윗면은 투명한 점선 면으로 남기고, `fillFraction`
  수면은 네 세로 모서리의 같은 비율을 보간한다. 미지 길이는 제출
  전 대체 치수로 좌표를 만들고 라벨을 `?cm`로 표시한다.
- 확인: 가로·세로·높이 조합의 투영 비율, 열린 윗면과 절반 채움
  요소, 미지 치수 좌표 마스킹을 단위 검사했다. 390×844 화면에서
  개념 직육면체 2개와 세트 A 10문항을 풀어 면·수면·열린 윗면·
  미지 높이, 가로 넘침·제출 전 정답 전용 값·콘솔 오류 0을 확인했다.
- 유지 계약: 겉넓이·부피 문제와 SVG는 같은 세 길이에서 파생한다.
  `openTop`은 윗면 제거 의미를 점선으로 보존하고, `fillFraction`은
  0~1 범위에서 실제 세로 모서리를 보간한다. 미지 길이는 제출 전
  좌표와 라벨 모두 정답값을 사용하지 않으며 계산 결과인 넓이·
  부피를 시각 설정이나 접근성 이름에 넣지 않는다.

## 띠 길이와 원 부채꼴을 따로 만들면 같은 비율이 다르게 보임

- 증상: 띠그래프의 구간 너비와 원그래프의 부채꼴 각도를 각각 고정
  좌표로 만들면 같은 40%가 서로 다른 크기로 보이거나 세 부문의
  합이 100%가 아닌 그림이 생긴다. 가린 비율 문제에서 숫자 라벨만
  숨기고 별도 답 속성을 남기면 제출 전 정답이 DOM에 노출된다.
- 원인: 부문별 백분율, 누적 시작·끝 위치, 원의 시작·끝 각도와
  보이는 라벨을 하나의 자료 모델에서 파생하지 않은 것이 원인이다.
- 실패한 접근: 띠그래프를 CSS 너비, 원그래프를 고정 SVG 경로로
  따로 조정하면 두 표현의 수치 계약을 함께 검증할 수 없다. 가린
  부문의 실제 백분율을 접근성 이름에 넣는 방식도 답 선노출이다.
- 대응: 세 부문 백분율을 누적한 `startPercent`·`endPercent`를
  만들고 띠 너비와 원의 3.6도/1% 부채꼴 경로를 같은 모델에서
  파생한다. 가린 부문은 숫자 대신 `?`만 표시하고 요소에는 부문
  순서 외의 답 전용 메타데이터를 두지 않는다.
- 확인: 모든 템플릿과 `p=2~4`에서 세 부문이 양수이고 합이 100%인지
  검사했다. 390×844 화면에서 개념 그래프 2개와 세트 A 10문항의
  띠·원 조각 각 3개, 가린 라벨, 정상 채점, 가로 넘침·답 전용
  메타데이터·콘솔 오류 0을 확인했다.
- 유지 계약: 문제·풀이·띠 너비·원 부채꼴은 같은 백분율 배열에서
  파생한다. 부문은 모두 양수이고 합은 100%여야 하며, 가린 값은
  제출 전 텍스트·접근성 이름·`data-*` 속성에 숫자로 넣지 않는다.

## 단위 이름을 읽는 미션만으로 단위 관계를 출시 처리하면 실제 범위가 비게 됨

- 증상: 3학년 원장은 `[4수03-21]`의 kg·g 관계를 출시 참조로
  표시했지만 실제 미션은 `2kg 300g`을 구조화 입력으로 다시 쓰는
  활동뿐이었다. 같은 단원의 들이 덧셈 미션도 `[4수03-19]`가 아니라
  단위 관계 기준에 연결되어 있었다.
- 원인: 원장은 단원 ID가 성취기준 문자열을 포함하는지만 확인했고,
  단원 안의 각 미션이 어느 관계·계산 활동을 실제로 수행하는지
  별도로 고정하지 않았다.
- 실패한 접근: 계획 상태였던 세 기준만 새 미션으로 추가하면
  원장 참조 수는 맞지만 kg→g 변환 학습은 계속 빠진다. 연산 결과를
  시각 설정에서 바로 라벨로 만들면 그림은 쉬워도 제출 전 정답이
  DOM에 노출된다.
- 대응: 기존 ID를 보존한 채 단원을 7개 미션으로 확장해
  `[4수03-17]`~`[4수03-23]`을 각각 한 미션 이상에 직접 배정했다.
  L/mL·kg/g 변환, 받아올림 들이 덧셈, t/kg 적용, 받아내림 무게
  뺄셈을 분리했다. 연산 그림은 주어진 두 양과 연산자만 먼저
  렌더링하고 결과는 성공 뒤 정답 문자열로 공개한다. t 그림은
  주어진 t 수만큼 실제 블록을 그린다.
- 확인: 단위 테스트가 7개 기준 집합, 40개 전체 미션, 난이도
  2/3/2, 네 t 블록, 변환·연산 결과 마스킹을 검사한다. 필수 게임
  클라이언트와 390×844 브라우저에서 7문항을 모두 풀었고, 결과
  `□`→정답 공개, 가로 넘침 0, 콘솔 오류 0을 확인했다. 전체 Vitest
  557/557, build 105/105, E2E 70/70이 통과했다.
- 유지 계약: 원장의 각 3학년 출시 기준은 해당 행동을 수행하는
  미션에 직접 나타나야 한다. 기존 미션 ID는 로컬 기록 호환을 위해
  유지하고, 정량 단위 그림에는 주어진 양만 넣으며 계산 결과는
  확인 전 DOM·접근성 이름에 만들지 않는다.

## 수의 범위 문장과 수직선을 따로 만들면 경계 포함 여부가 뒤집힘

- 증상: `이상`·`이하`와 `초과`·`미만`을 같은 점으로 그리거나,
  한쪽 범위의 선을 양쪽에서 닫으면 문제 문장과 그림이 서로 다른
  자연수 집합을 나타낸다. 범위에 들어가는 수의 개수를 그림 속
  라벨로 먼저 계산하면 정답도 제출 전에 노출된다.
- 원인: 경계값, 포함 여부, 범위 방향과 수직선 좌표를 문제의 수학
  모델에서 함께 파생하지 않고 문장과 SVG를 별도로 작성한 것이
  원인이다.
- 실패한 접근: 포함 여부를 난이도 신호에 반영하지 않은 첫 감사는
  양쪽 경계 제약의 추가 사고 단계를 인식하지 못해 Applying 평균이
  Knowing보다 낮게 나왔다. 닫힌 점 하나만 공통 그림으로 재사용하는
  방식은 초과·미만의 의미를 왜곡한다.
- 대응: `number_range`에 시작·끝, 선택적 아래·위 경계, 각 경계의
  포함 여부만 전달한다. 렌더러가 한쪽 범위에는 방향 화살표를,
  양쪽 범위에는 선분을 그리고 포함 여부에 따라 닫힌 점·열린 점을
  선택한다. 품질 감사는 양쪽 경계 조건을 실제 복합 제약으로
  계산한다.
- 확인: 생성기 재실행 바이트 일치, 30개 템플릿의 A/B/C 10문항·
  K4/A4/R2·difficulty 4/4/2, 난이도 신호 5.61 < 6.36 < 7.33을
  검사했다. 390×844 실제 화면에서 세트 A 10문제를 풀며 네 경계
  표현과 단방향 화살표, 답 선노출·가로 넘침·콘솔 오류 0을
  확인했다. 전체 E2E 71/71도 통과했다.
- 유지 계약: 문제·풀이·정답·범위 그림은 같은 경계값과 포함
  boolean에서 파생한다. 포함 경계는 닫힌 점, 제외 경계는 열린
  점이어야 하며 한쪽 범위는 올바른 방향으로 계속됨을 표시한다.
  정답인 개수·첫째 수·마지막 수는 제출 전 시각 설정·텍스트·
  접근성 이름에 넣지 않는다.

## 분수 막대의 칸 수와 문제 분모를 따로 두면 크기 비교가 왜곡됨

- 증상: 분모가 다른 두 분수에 폭이 다른 막대를 쓰거나 고정 칸
  그림을 재사용하면 색칠된 길이만 보고 비교한 결과가 실제 분수
  크기와 달라질 수 있다. 더 큰 쪽이나 교차곱을 그림 속 속성으로
  미리 저장하면 정답도 제출 전에 노출된다.
- 원인: 두 분수의 전체 길이, 분할 수, 색칠 수를 각각 조정하고
  문제의 분자·분모와 같은 모델에서 파생하지 않은 것이 원인이다.
- 실패한 접근: 첫 품질 감사에서는 추론 문항이 분자나 분모만 보는
  오류를 찾은 뒤 큰 분수를 고르는 데서 끝나 Applying보다 신호가
  낮았다. 오류 이름만 붙이는 것은 실제로 방법을 설명하고 검증하는
  난이도 있는 추론이 아니었다.
- 대응: `fraction_comparison`은 두 주어진 분수만 받아 같은 폭의
  막대를 각 분모 수만큼 나누고 분자 수만큼 색칠한다. 추론 문항은
  잘못 고른 비율을 여러 번 사용했을 때의 누적 차이를 통분과
  교차곱으로 검증하도록 바꿨다.
- 확인: 모든 허용 매개변수에서 30개 템플릿의 답·선택지·문장·
  시각을 검사했고 난이도 신호 4.48 < 5.36 < 9.57과 감사 오류·
  경고 0을 확인했다. 390×844 화면에서 개념 2/3·3/5 막대와 세트
  A 10문제를 풀어 칸 수·색칠 수, 채점, 가로 넘침·답 선노출·
  콘솔 오류 0을 확인했다. 전체 E2E 72/72도 통과했다.
- 유지 계약: 두 막대의 전체 픽셀 길이는 같고 각각의 칸 수와
  색칠 수는 해당 분모·분자와 같아야 한다. 시각 설정에는 비교
  결과, 더 큰 쪽, 차, 교차곱, `answer`·`result`·`target` 같은
  답 전용 값을 추가하지 않는다.

## 넓이 단위를 길이처럼 한 번만 바꾸면 변환 배수가 틀림

- 증상: 1m=100cm라는 길이 관계만 한 번 곱하면 1m²를 100cm²로,
  1km²를 1000m²로 잘못 바꾸게 된다. 변환 결과를 그림 안에 미리
  적으면 기본 변환 문항의 정답도 제출 전에 노출된다.
- 원인: 넓이가 가로와 세로 두 방향의 곱이라는 모델을 단위 변환과
  연결하지 않고 단위 문자열만 치환한 것이 원인이다.
- 실패한 접근: 100×100개의 실제 작은 칸을 SVG에 모두 만들면
  의미는 정확하지만 모바일 DOM이 과도하게 커지고, 1000×1000은
  현실적으로 렌더링할 수 없다. 10×10 격자를 실제 작은 단위 칸으로
  설명하면 수량 자체가 틀린 그림이 된다.
- 대응: 큰 단위 한 변의 정사각형을 그리고 가로·세로 양쪽에 같은
  길이 관계를 표시한다. 내부 격자는 크기 구조를 돕는 장식으로만
  두고, 텍스트는 `100cm×100cm` 또는 `1000m×1000m`까지 보여
  주며 계산 결과는 렌더링하지 않는다.
- 확인: 두 단위 쌍과 모든 허용 매개변수에서 정·역변환, 직사각형,
  혼합 넓이, 한 방향·한 변 누락 오류를 검사했다. 난이도 신호는
  8.40 < 9.38 < 10.81이고 감사 오류·경고는 0이다. 390×844
  화면에서 두 개념 시각과 세트 A 10문제를 풀어 정답 선노출·
  가로 넘침·콘솔 오류 0을 확인했다. 전체 E2E 73/73도 통과했다.
- 유지 계약: 넓이 변환은 길이 변환 배수를 두 방향에 각각
  적용한다. 시각은 큰 단위 정사각형과 두 변의 길이 관계만
  전달하고 `10000`, `1000000` 같은 제곱 결과나 `answer`·
  `result`·`target` 필드를 제출 전에 포함하지 않는다.

## 사건 횟수만 비교하면 전체 횟수가 다른 자료의 가능성을 왜곡함

- 증상: 사건이 일어난 횟수가 더 많은 자료를 무조건 가능성이 큰
  자료로 고르면 전체 시행 횟수가 다른 두 기록을 잘못 비교한다.
  관찰 비율이나 다음 시행의 예상 횟수를 그림에 미리 계산해 넣으면
  응용·추론 문항의 답도 제출 전에 노출된다.
- 원인: 사건 횟수, 전체 시행 횟수, 가능성, 자료 크기, 예상 횟수를
  하나의 자료 모델로 구분하지 않고 원시 횟수만 비교하거나 그림과
  풀이에서 별도로 계산한 것이 원인이다.
- 실패한 접근: 초록 칸의 절대 개수만 강조하면 전체가 큰 자료가
  더 유리해 보인다. 같은 비율의 두 자료를 동일한 크기의 띠로
  정규화하면 자료 수가 많은 기록을 판단 근거로 선택하는 문항의
  핵심 정보가 사라진다.
- 대응: `possibility_trials`에는 각 기록의 라벨·사건 횟수·전체
  횟수만 전달하고 전체 수와 같은 개수의 칸을 그린다. 비율 비교,
  자료 수 판단, 예상 횟수와 두 자료를 합친 결과는 문제의
  solver와 풀이에서 계산하며 시각 payload에는 저장하지 않는다.
- 확인: 모든 허용 매개변수에서 30개 템플릿의 답·선택지·문장·
  시각을 검사했고 난이도 신호 3.11 < 3.64 < 6.26과 감사 오류·
  경고 0을 확인했다. 390×844 화면에서 개념 시각과 세트 A의
  초기·답 선택·힌트 상태를 검토해 정답 선노출·가로 넘침·콘솔
  오류 0을 확인했다. 전체 E2E 74/74도 통과했다.
- 유지 계약: 문제·풀이·정답은 같은 사건 횟수와 전체 횟수에서
  파생한다. 시각에는 관찰된 두 수만 넣고 비교 결과, 기약분수,
  예상 횟수, 합친 비율, `answer`·`result`·`target` 같은 답 전용
  값을 제출 전에 추가하지 않는다.

## 검수 화면의 정렬과 입력 폭을 브라우저 기본값에 맡기면 hydration과 모바일 검수가 어긋남

- 증상: 전 학년 검수 화면에 문제군 등 한국어 필터를 추가한 뒤
  서버 HTML의 option 순서와 브라우저 hydration 순서가 달라
  React가 전체 문서를 클라이언트 렌더링으로 교체했다. 390px
  화면은 페이지 가로 스크롤이 0인데도 select 자체가 415px이 되어
  카드 오른쪽에서 잘렸다.
- 원인: `localeCompare`의 정렬 결과가 Node ICU와 Chromium에서
  같다고 가정했고, select의 브라우저 기본 최소 너비가 긴 option
  텍스트를 따라 커지는 것을 부모의 `overflow-x-hidden`이 가렸다.
- 실패한 접근: `documentElement.scrollWidth <= innerWidth`만
  검사하면 잘린 내부 컨트롤을 찾지 못한다. 단위·E2E 성공만 보고
  실화면의 console과 필터 위치를 다시 보지 않으면 hydration
  재렌더링도 통과한 것처럼 보인다.
- 대응: 필터 값은 로케일과 무관한 코드포인트 비교로 결정적으로
  정렬한다. 모든 필터 label에 `min-width: 0`, 입력에
  `width: 100%; min-width: 0; max-width: 100%`를 적용한다.
  E2E는 console/page error 0과 각 필터의 실제 좌우 경계가 viewport
  안인지 함께 검사한다.
- 확인: 390×844에서 필터 너비가 415px에서 316px로 줄고 오른쪽
  경계가 353px에 머무는 것을 캡처했다. 1024×768 실제 직육면체
  전개도 경계 변형에서도 가로 넘침과 console 오류가 0이었다.
  전체 Vitest 679/679, build 113/113, E2E 77/77이 통과했다.
- 유지 계약: SSR되는 선택지 정렬은 실행 환경의 locale에 의존하지
  않는다. 페이지 가로 스크롤 검사와 별도로 모든 모바일 필터의
  bounding box를 검사하며, hydration·console 오류 0을 검수 화면의
  필수 게이트로 유지한다.
